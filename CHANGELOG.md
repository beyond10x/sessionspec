## [Unreleased]

### Added

- A secret as a read-only file of a unit (R120): a binding may give a unit a secret as a file, `secret_files: [{secret: <name>, key: <key>, path: <absolute path>}]` on a unit `packing.units` lists or on a part under `parts:` (`key`, optional, the one key of the secret the file holds). `agenticspec deploy bundle` carries them in the unit's `config` beside `env` and `args`, sorted by `path`, by the secret's name, never a value. `deploy bundle` and `deploy check` refuse a secret that no part of the unit declares (`secret_undeclared`) or that is no secret name (`secret_value`), an entry of the wrong form or a relative `path` (`unit_config_invalid`), and two secret files at one path or a secret file at, around or inside a volume mount or a scratch directory of the unit (`unit_mount_collision`). A binding without `secret_files` gives the same bundle bytes as before
- Scratch directories of a unit (R118): a binding may give a unit a writable directory at a fixed path that lives as long as one instance and holds nothing after a restart, `scratch: [{mount: /run/flow, size: 64Mi}]` on a unit `packing.units` lists or on a part under `parts:` (`size` optional, text like a volume's size). `agenticspec deploy bundle` carries them per unit as `scratch`, sorted by `mount`, with no volume claim. `deploy bundle` and `deploy check` refuse a scratch directory at the mount of a volume of its unit or of another scratch directory, or one that holds the other or lies inside it, comparing paths by segment (`unit_mount_collision`), and a `scratch` of the wrong form, a relative `mount` among them, or on a part in no unit (`unit_scratch_invalid`); `deploy check` also refuses a unit's `scratch` that is not the one its binding resolves. A binding without `scratch` gives the same bundle bytes as before
- Outside writers of a runtime's durable state (R109): a `runtime` part with `durable_state: true` may name the programs outside the runtime that also write that state, `state_writers: [<name>, ...]` (a non-empty list of texts). The deployment bundle still claims one volume for it, `<part>-state`, with the same access (`read_write_once` in a unit of one copy), and derives no workspace lease or proposal port, as it would for a shared workspace; the claim lists the writers (`writers`), and the architecture page shows them with the part. `agenticspec sim check` refuses `state_writers` that is not a non-empty list of texts, or that stands without `durable_state: true` (`setting_invalid`). The settings table takes `type: string` with `list: true`. A runtime part without `state_writers` gives the same bundle bytes as before
- A binding may name the path a UI reads its upstream's adapter at: `ui.<ui>.upstream.path`, for the operator UI, the control-plane UI and a UI of your own. `agenticspec deploy bundle` writes it into the UI unit's `upstream.path` and, for the operator and control-plane UIs, into the `api_base` of the built archive's `config.json`; the archive of a UI of your own is carried as it is. Without `path` both stay `/api/` and the bundle is the same bytes as before. A path that does not start with `/` is refused by `deploy bundle` and, in a written bundle, by `deploy check` (`ui_upstream_path_invalid`); a `path` that is no text is a binding of the wrong form (R100)
- Free notes on a part: every part may carry `notes`, a map with keys and values of any kind for what no setting of its block types (a channel's file, path or audience, an agent's model or use). `agenticspec sim check` takes any map there as written and refuses only a value that is not a map (`setting_invalid`); the simulator, the search (a number or a `vary` key in the notes marks no place) and the contract never read it. New typed settings: a channel of kind `screen` (a page of a user interface), a pool of kind `queue` and a pool's `order` (`fifo`, `lifo`, `priority`), a model's `hosting` (`vendor`, `managed`, `local`, the block's own enum) and `billing` (`subscription`, `metered`, `none`), a spend cap on an `authority` or `runtime` part (`per_day_usd`, `per_month_usd` in USD, and `route`: `stop`, `ask` or `notify` at the cap), and a `question` part's `default` and `default_after` (a duration). (R97)
- `agenticspec ui generate --path <document> --out <dir> --project` writes a project that builds the app of an `ess-ui/1` document on its own (R101): the app under `src/generated/`, the kit's sources under `kit/`, a host page with a placeholder per host slot, a vite config with the operator UI's output options, an npm manifest and lock with the versions of vue, vite and its vue plugin the operator UI of `ui build` is built with, and a packer. On a host with node, `npm ci && npm run build` in it writes `dist/` and `dist.tar`, packed as `ui build --archive` packs, and prints the archive's sha256: the `{archive, digest}` a binding's `ui.<name>.source` names. `source: {ess_ui}` stays refused with `ui_build_needs_toolchain`.
- A region of the render model can be `collapsed: true`. The page then draws it as one card with its label and the count of the nodes inside it (nested regions included); a refusal inside rings the card. Edges between two collapsed regions, or between one and a node outside it, are drawn once per pair of visible ends and read `×<n>` when they stand for more than one edge. Selecting the card (click, Enter or Space; a button named "Open region <label>, <n> nodes") opens the region in place with its nodes and every edge on its own, and a `close` control on its frame or band closes it again. A region inside an open one stays collapsed until it is opened itself; one collapsible region is open at a time, with those around it. Every state is laid out in full when the page is written, so the page needs no server, and without its script it shows every region collapsed. A `collapsed` that is no boolean is refused with `region_collapsed_invalid`, a collapsed region that holds no node with `region_collapsed_empty`
- `agenticspec sim render` also draws a render model page: given a file of format `agenticspec-render-model/1` (JSON or YAML), it writes that page; a page the model's check refuses is `document_unreadable` with the refusal
- `agenticspec ui generate` draws more of released `ess-ui/1` (R108): a read's row predicate `reads.filter` in the ess-ui grammar (`==`, `!=`, `in [..]`, `contains`, `not`, `and`, `or`, parentheses; over `row`, `state`, `params`, `shell` and widget `args`), so two panels of one view with different filters stay two sections, a search box per `contains state.<name>`; a collection's `sort: {by, dir}`; `group_by`, `group_order` and `show_empty_groups`; `style: cards` (drawn as a list); `reads.refresh` as a poll interval; a page's `actor` (checked, not drawn); `header.help {text, link}` and `header.metrics`; the `metric` component (`aggregate`, `field`, `match`, `format: number`); row action `as: icon`; an action's `confirm: {title, confirm_label, show}`, asked in place; form field `as: choice`. Every other construct of released `ess-ui/1` is still refused by its node path; the ui generate section of `docs/deployment.md` lists them with their refusal message. The runtime of a generated app gains the predicate, sort, group, poll, metric and confirm helpers, so committed generated apps change. Golden case `rows`
- `agenticspec ingress project` writes the projection of every export, not only `http`: per `event_stream` export the stream list (`<ingress>.streams.yaml`, every event of the feeds, resumed from a cursor, `CursorExpired`), per `cli` export an `ess-cli/2` binding (`<ingress>.cli.yaml`, a command `<domain> <wire name>` per command and view forwarded to the component that serves the blocks, one `--option` per field; ESS 0.99.2 cannot yet resolve the input and row types it names, `design/ess-repro/cli-service-forward/`), per `tool` export the tool list (`<ingress>.tools.yaml`, one tool per command and one read tool per view named by its ESS wire name, with its description, a standalone input schema and the ESS errors of a command), per `agent` export the agent card (`<ingress>.agent.yaml`, one skill per command, the feeds as updates) and per `metrics_scrape` export the metric list (`<ingress>.metrics.yaml`, every KPI a gauge with its catalogue unit and summary, labels architecture, part path and instance). A projection the blocks, their OpenAPI document or the KPI catalogue cannot give is refused naming each operation (`projection_refused`). The worked example's stream lists, the operator's tool list and the metric list are committed under `architectures/projections/workstation-ingress/` and held by `check:projections`
- `agenticspec ui conform` sends on every write what a page of the source's origin sends: `Origin`, the origin of `--source` (`--origin <url>` sends another), and each `--header 'Name: value'` (repeatable), such as a CSRF token. A source that accepts only same-origin writes now carries out the command instead of refusing every one. A malformed origin is refused with `origin_invalid`, a malformed header, `Origin` or a header the suite sets itself with `header_invalid`. When a check fails, the command prints every check on a line of its own (`passed|failed|skipped <name>: <detail>`) before the refusal, whose detail now also counts the passed and skipped checks; `--json` prints the report (every check with its status and detail) instead, also when a check failed (R90)
- The runtime interface (`ui/runtime.openapi.yaml`) declares the answer of a source that does not serve a view: 404 with `{"error": "view_not_served", "view": "<view>"}`. `ui conform` counts such a view as skipped, by its name, in both modes; any other 404 of a view read still fails. `ui serve` serves every view and never sends it (R91)
- A row or change signal that names no entity can carry a top-level `scope`, the scope id it belongs to (`{architecture_id}[/{part path}[/{instance}]]`). When it holds a scope of the architecture it decides over the entity-id rule: the row is in scope at that scope and the scopes above it. `ui conform`'s scope checks (and, in the mode with an architecture, a row whose `scope` lies outside the scope read), the fixture source and `ui serve` (on fixtures and with `--sim`, rows and events) honour it; a view may carry the field without declaring it. A field of that name holding anything else, such as a store's `scope: Part`, leaves the entity-id rule in force (R92)
- `agenticspec ui serve <architecture> --sim <profile>` answers a simulator run instead of fixtures. The architecture is simulated once at the values it is built with, under the profile, with seed 1 for one day. R1 answers each view from the state the run's events left: one row per entity, with its identity and its state, read from the blocks' outcomes. A row is shown at the scopes of the parts where its events happened. R2 replays the run's event log (the lines of `sim run --events`) in order, and each event's `seq` is its cursor. The Metrics page shows the run's KPIs. `agenticspec ui conform --architecture` passes against it. `--sim` together with `--fixtures` is refused with `sources_conflict`, and a profile the simulator refuses with `simulation_refused`
- One operator UI per ingress with a `ui` export: when the contract gives a `ui` export to an ingress other than `operator`, `agenticspec ui derive` writes one composition per such ingress, `<name>.<ingress>.ui.yaml` (listed under `ingresses`), each scoped to the ingress's interface: only the panels of its views, only its commands as actions (a command no link places becomes a row action on its domain's panels), only its feeds on the channels. `agenticspec ui build --ingress <name>` writes that UI, `config.json` naming the ingress. `agenticspec ui serve` serves each at `/ingress/<name>/` with its own plane below `/ingress/<name>/scopes/`, R5 listing only that ingress's commands, and the operator app at `/ingress/operator/` as well as `/`; with `--sim` each answers from the one simulator run, kept to its own views, channels and feeds. An architecture whose only `ui` export is the operator ingress's keeps its one operator UI byte for byte. Golden examples `workstation-ingress.user.ui.yaml` and `workstation-ingress.operator.ui.yaml` are under `ui/views/examples/`, held by `task check:ui`
- Durable state of a runtime part (R88): the setting `durable_state: true` on a `runtime` part (boolean, default false) says the service keeps records of its own across restarts. In a deployment bundle its unit claims an exclusive volume `<part>-state` (`read_write_once`), mounted where the binding's `parts.<p>.volumes[].mount` says and sized by `parts.<part>.size`, as a workspace's volume is; without an absolute mount it is refused `volume_mount_missing`. A runtime part with durable state in a `job`, `scheduled` or `model` unit, or whose state volume's name is taken by a part, is refused `durable_state_unplaceable`, by `deploy bundle` and `deploy check`
- Requirements: a top-level `requirements:` key of an architecture, entries `{kpi, at_least | at_most | equals, part?, window?}`, outside the nesting digest and the revision digest. `agenticspec sim check` refuses a KPI id no stage knows (`requirement_kpi_unknown`) and an entry of the wrong form (`requirement_invalid`), and prints each requirement under `requirements` with its stage (`check`, `evaluation`, `operation`, `cloud`), its state (`met`, `missed`, `undecided`) and its value: a KPI of the architecture as a whole or a gate count is decided at check; a missed one is reported and does not refuse the document. A cloud KPI is written `cloudspec:<id>`. `agenticspec sim run` decides each requirement on what the simulator measures; the search ranks a feasible variant by requirements missed before its fitness, `fit` stops after the round in which a variant first meets them all, and the result carries each requirement's state (`requirements`, `baseline.requirements`, `best.requirements`, `variants[].requirements_missed`). A result without requirements is the same bytes as before
- `agenticspec deploy bundle` carries every document a nested architecture references, the nesting chain resolved, in `nested`: keyed by its canonical digest (the pin), with the parts that refer to it, its exact bytes in `content_base64` with their `sha256`, and the parsed `document`; the units, packing and contract read the architecture flattened. `agenticspec deploy check` resolves the architecture from those documents and refuses a pin the bundle carries no document of (`nested_document_missing`) and a carried document whose bytes or digest do not hold (`nested_document_mismatch`). The bundle's `requirements` are checked like `sim check` does (a refusal is a finding of `not_admitted`) and each carries its stage, state and value. New fixture: `bundles/team-with-console.local.yaml`
- A part's settings are typed per block, from one table (`blocks/settings.yaml`): each setting a part of a block may carry, with its type (number or integer with unit and range, boolean, enum, duration, string, the name of another part, shares), its default and the contract ports it narrows; an enum is the block's own where the block declares one (a pool's `kind`, a sandbox's `isolation`). `agenticspec sim check` refuses a setting the part's block does not declare (`setting_unknown`) and a value outside its type or range (`setting_invalid`, for example `capacity: many` on a pool), each naming the part, the setting and what was expected; both are gate KPIs, so every variant in `result.json` counts them. The contract copies the settings the table marks, and each block page of the docs site lists its settings with type, unit, default and the ports they narrow
- A UI of your own in a deployment bundle: any key under a binding's `ui:` other than `operator` and `control-plane` is a UI you built, `ui.<name>: {source: {archive: <file>, digest: sha256:<hex>}, export: <ingress>.<protocol>, upstream?, port?, bind?}`. `agenticspec deploy bundle` adds the unit `<name>` (`kind: service`, `roles: [ui]`, static code) and carries your archive byte for byte in `files`, beside the operator and control-plane UIs. It refuses an archive that is not its digest (`ui_archive_mismatch`) and an export no ingress has (`ui_export_unknown`). `source: {ess_ui: <file>}` is refused with `ui_build_needs_toolchain`, because the pages `ui generate` writes need node and vite to build; name the archive you built instead. The accepted list holds the role `ui`
- The control-plane UI: `agenticspec ui derive --control-plane` and `ui build --control-plane [--prediction <result.json>]` add pages across parts beside the operator UI. The pages are Inbox, Activity, Operations, Metrics (each KPI with the simulator's prediction of the same revision), Architecture (read-only) and Events (the level's channel as a live log), plus tiles on the overview. They are selected by port class and by the configuration/administration split, never by view name. A configuration command, a command only report-issuing actors may issue, and machine traffic are never offered. `ui serve` serves the control-plane UI at `/control/`, and `ui conform --architecture` checks its reads. A binding's `ui: {control-plane: {port, bind, upstream}}` adds the bundle unit `control-plane-ui` (`roles: [control-plane-ui]`, static code), which can run beside `operator-ui`. Golden examples for `workstation` and `team-with-console` are under `ui/views/examples/`, held by `task check:ui`
- `agenticspec ui serve` and `agenticspec ui conform --architecture` work from a released binary alone, in any directory: the fixtures they answer from (every view fixture, channel script and scripted outcome, about 114 KB) are built into the binary, and the contract is derived with the port and KPI catalogues built into it. `ui serve --fixtures <dir>` answers from a directory of your own (`<view>.json` files, `scripts/`, `outcomes.json`); `fixtures_unreadable` now refuses only such a directory
- `agenticspec ui serve <architecture> [--contract <file>] [--port <n>]` shows the operator UI of an architecture with no runtime: it derives the default control plane and serves it on 127.0.0.1 (port 7430 by default), the operator app at `/` and the runtime interface below `/ingress/operator` answered from fixtures: R1 from the block fixtures, R2 from the channel scripts with resume from a cursor, R4 recorded (`/fixture/commands`) with the outcomes of `ui/views/source/outcomes.json`, R5 allowing every action
- `agenticspec ui conform --architecture <file> [--contract <file>] [--source <url>]` checks a running server, such as a runtime's own adapter, against the default control plane of an architecture with no plan: each part's views answer rows of their declared shape, the level's channel resumes from a cursor without repeating an event, R4 carries out what R5 allows and refuses what it withholds, R5 answers at every scope, and a request without credentials gets 401. It exits non-zero and names each failed check; `docs/deployment.md` shows how a runtime proves it answers the interface

- The building blocks declare their cross-block causation as ESS bindings (`blocks/components.yaml`): an admitted gateway call starts its inference, and the authority's decision, approval or rejection decides a harness tool call. `task check:layers` counts bindings among the dependencies, and `task check:blocks` requires a scenario per binding. Causations ESS cannot express yet have reproductions under `design/ess-repro/`
- `agenticspec sim ports` derives the ports of the building blocks, where the specification waits on the world, into `blocks/ports.json`: each port's kind (outbound, clock, principal), intent, reports and protocol. `--check` compares the file's digest with the blocks without calling `ess` (`task check:ports`), `--expect` lists every difference from an expected list
- `agenticspec sim contract <architecture>` derives and checks the contract of an architecture (`agenticspec-contract/1`): the ports its parts use with their protocols, narrowing settings (an agent's `role`, an `on_event` trigger's `event_name` and `source`) and instances, a routing invariant per link (a runtime's `run` and `model_call` links among them) in a small predicate language, and the border; `--check` checks a written contract. `docs/contract.md` describes ports, the contract and the predicate language
- Every architecture page and catalog entry of the docs site has a "Contract" section and its contract file to download (`<name>.contract.yaml`)
- KPIs of an architecture as a whole, read from its document before any simulation: `agents_total`, `principals_total`, `human_touchpoints`, `autonomy_depth`, `model_call_paths`, `ungated_model_calls`, `single_points`, `border_parts`, `egress_targets`, `shared_workspaces` and `capacity_ratio`. `agenticspec sim check` reports them (and names the single points), `result.json` carries them for every variant, the KPI catalogue lists them under the block `architecture`, each architecture page and catalog entry has a section "The architecture as a whole", and the catalog index compares every architecture on them in a sortable table
- agenticstudio is live: every query, apply, check and simulate on a draft is a tool call of a studio session (`/api/sessions`), each new revision and each answered call reaches every page open on the draft at once over its event channel (`/api/drafts/<id>/events`), and a draft's revisions can be listed and read (`/api/drafts/<id>/revisions`). When the architecture file a draft was opened from changes on disk, the change becomes the draft's next revision on every open page. `simulate` answers the mean of each KPI over a few seeds with what the KPI catalogue says it measures
- `agenticstudio-mcp`, the agent channel: an MCP server over stdio whose tools `query`, `apply`, `check` and `simulate` drive a draft of a running `agenticstudio serve`; a refusal names the rule and the error, a simulate explains each KPI, and every page open on the draft shows each change live (`docs/studio.md`)
- `agenticspec sim check --json <architecture>` prints one `agenticspec-check/1` JSON document on standard output, also when the architecture is refused: `valid`, every violation with its `rule`, `gate`, `subject` (the part, or the link as `<from>-><to>:<carries>`), `part`, `link` and `message`, sorted, and the count of every rule. The exit code and the output without `--json` are unchanged
- `agenticspec sim` simulates more of an architecture: an agent that reaches several model parts splits its calls by its `model_share` and each call is priced by its model's route; a runtime part given runs (a `run` or `order` link, or a trigger) executes their steps, model calls and person steps; an `on_event` trigger fires when the simulation emits its event (`agentic.work.TaskCompleted` and seven more), optionally only for the part its `source` names, and a trigger may wake a runtime
- `agenticspec ui generate --path <doc> --out <dir>` turns an `ess-ui/1` document into a Vue app (pages, router, typed client) over the design system `ui/kit`, refusing any construct it cannot draw by its node path. agenticstudio's page is now that app (`ui/studio`, from `studio/studio.ui.yaml`): the graph fills the page inline with pan, zoom and part selection, a side panel holds the patch, the draft and the parts, one theme switch covers it all, and every control looks like the docs site. `agenticstudio serve` takes `--www` and answers `/api/views` and `/api/commands`; `task studio:build` builds the app, `task check:ui-kit` and `task check:studio` gate both
- agenticstudio, first slice: `agenticstudio serve --root <dir> --port <n>` opens an architecture of `architectures/` as a draft in the browser, applies a patch (`agenticspec-patch/1`: `set` and `add` over the facts `part`, `setting`, `link` and `marker`) as one revision or refuses it whole with the rule's position and error, and shows the graph, the parts and the check. Drafts are held in memory. `task check:studio` runs its browser test (`docs/studio.md`)
- The architecture block records where an entity of a lower block sits: `agentic.architecture.Placement` (architecture, revision, part path, copy, entity name and id), recorded by the runtime through `PlaceEntity` and read through the view `Placements`, filtered by part path, copy and entity name. A row of any block view is in scope of a part when its own id, or an id field of its view one hop away, is placed to that part
- `agenticspec ui panels` writes the block panels from the building blocks: `ui/views/blocks.ui.yaml`, an `ess-ui/1` document with one panel per view of `blocks/` (its fields as columns, its first field as row key, an enum such as `state` as a badge, live updates from the events of the view's entity, a scope of architecture, part and instance) and a gallery page per block, the fixtures the panels render against in `ui/views/fixtures/`, and the digest of its inputs in `ui/views/blocks.sources.sha256`. `--check` compares a fresh generation byte for byte; `task check:ui` runs it and holds `ess ui check --model blocks` at 0 errors and 0 warnings
- `blocks/components.yaml`: one component owning every block, served over HTTP, and a `Viewer` actor for the agent, architecture, delegation, experiment, KPI, principal and process blocks, so every view of `blocks/` is readable from an `ess-ui/1` document
- Nested architectures: a part `{ block: architecture, ref: <file>, digest: sha256:<hex> }` is another architecture document, and a link reaches one of its border parts as `<part>.<border part>`. `agenticspec sim check` resolves the references recursively and refuses a missing file, a digest mismatch (expected and actual), a cycle, an address off the nested border and a nested document its own check refuses; its output lists the nested architectures with their digests. `agenticspec sim digest <file>` prints the pin: the SHA-256 of the canonical JSON of the document's parts, links and border. The simulator flattens a nested architecture into parts named `<part>.<inner part>`, renaming the parts an inner `model_share` or trigger `source` names; an inner part keeps its `role`; the graph draws it as one box with its border parts as ports. Example: `architectures/team-with-console.yaml`, which nests `architectures/console.yaml`; its steward has `role: orchestrator`, and `profiles/coding.yaml` gives that role an `answer_seconds` so the steward answers the agents it orders
- `agenticspec ui generate` draws the block panels: one Vue component per widget of the document (`widgets/<Widget>.vue`, the same file for the same widget in every document) with its parameters as props, a page section that uses a widget with its arguments, a navigation region as the docs site's sidebar (a Pages button on a narrow screen), `live` with `effect: refetch` coalesced over `coalesce` and `effect: insert_or_patch` by `match` (with `only_if: matches(params)`), `as: json`, and a widget's scope (`source`, else `/scopes/<architecture>/<part>/<instance>` under the app's own base); every other construct is refused by its node path. A document that names no theme follows the system theme. `ui/views/gallery` is the gallery of the block panels over their fixtures, with no server: `task views:build` builds it, `task check:views` runs its unit tests and its browser test (every panel shows its fixture rows; axe-core and overflow at 1366x768 and 390x844 in both themes). The kit shows a UUID short, a JSON value by its entries and a named state by its name, and a table that scrolls sideways can be reached by the keyboard
- The runtime interface of the generated UI, `ui/runtime.openapi.yaml`: reads, a channel resumable from a cursor, the placement views, commands and the action set, at `{root}/scopes/{architecture_id}[/{part path}[/{instance}]]`, each request authenticated. `agenticspec ui conform [--source <url>] [--plan <file>]` checks an adapter against it (scoped reads, resume from a cursor, refusals, the action set against the grants, a request without credentials), against the fixture source of `ui/views/source/` when no source is given; the gallery answers a scoped widget the same way
- An action that sends a command shows only while the action set of its scope (`GET {source}/api/actions`) allows the command, and an action takes `visible`, which may read `actor.may(<command>)`; a source without an action set shows every action. The generated client sends the cookies of the host's sign-in, also to a source on another origin
- `agenticspec sim contract <architecture> --suite <suite.json> --out <cut.json>` cuts the conformance suite of the building blocks to the scenarios about a command of a port of the contract, and `task contract:conform -- <architecture.yaml>` runs the cut of the cached suite on the ESS interpreter, printing the count kept against the whole suite (`architectures/workstation.yaml`: 195 of 702)
- `agenticspec sim trace <architecture> --profile <profile>` writes the port uses of one simulated run as a trace (`agenticspec-trace/1`): model calls inside their gateway calls, build claims, questions and their forwards, channel deliveries, posts and trigger firings, with begin, end, nesting and counterparty. `agenticspec sim contract <architecture> --trace <trace>` checks every routing invariant of the contract on it: `held`, `violated` (naming the link and the event, exit 1) or `not_checked` when the trace does not record a port the invariant names
- An architecture document may declare its ingresses (`ingress:`): per audience (a principal part) an interface that selects commands (`principal`, `plays` of an actor's administration commands), views, feeds and KPIs, and its exports (`http`, `event_stream`, `cli`, `tool`, `agent`, `metrics_scrape`, `ui`). `agenticspec sim check` refuses an ingress by 14 named rules, reading `blocks/ports.json` (`--ports`) and `kpis/catalogue.yaml` (`--kpis`), and `agenticspec sim contract` writes each interface resolved into operations in the contract's `ingress` section. `architectures/workstation-ingress.yaml` is the worked example
- `blocks/ports.json` lists each actor's commands and per domain its commands with their role (internal, report, intent, configuration, administration), its views and its events
- The architecture block declares `Ingress` and `Export` with `AddIngress`, `AddExport` and the `Ingresses` view, and a contract records its ingresses
- Run and runtime lifecycle in the building blocks: a new block, `deployment` (layer 9), installs an architecture revision on a runtime, drains it (no new runs, started runs end) and rolls it back to the installation it replaced; an architecture run is queued, running, waiting, done, failed or cancelled and keeps the revision and binding it was queued under. A run, a firing and a harness session take their identity from the caller, so a repeat is refused and starts nothing. A trigger declares what a firing does for a subject that already has a started firing (another, skip, queue, replace). A tool result or an answer that could not be read is recorded as such (`CouldNotRead`), and a restarted session records the session it replaces and the lineage it belongs to (`RecordRestart`). ### Changed

- `agenticspec ui derive` runs in any directory, from a released binary alone: the compiled building blocks, the block panels with their scripts and digest, and the port catalogue are built into the binary, so it needs neither a checkout nor `ess`. It writes the same files as before. `--root <checkout>` still reads `blocks/` (compiled with `ess`) and `ui/views/` from a checkout instead
- A rendered graph (a render model page, an architecture page, a catalog entry) wraps a wide row: the cards of one row of a page or a band, and the cards a region's frame holds, that side by side would be wider than 2400 px (twice a reference view of 1200 px) go into as many rows as keep each within it, shared out evenly, in the order the one row had, read row by row. Edges to and between the new rows are routed as between any two rows and stay out of the cards they do not end at; in a region's frame, an edge leaves a line through the gap below it and a corridor beside the lines. A band of 65 nodes in one row that was about 60 times wider than tall now stands in rows; the 109-node test fixture went from 12408 × 5492 px to 2416 × 6252 px (its opening zoom in a 1200 × 638 view from 0.097 to 0.102, now bound by its height, which the lanes of the edges between bands set). A row that fits is drawn as before, byte for byte
- A page in bands draws the edges between two bands on shared lanes: edges whose runs through a gap lie apart (at least 16 px between them, label included) share one lane, and edges with one label out of one card, or into one card, run as one bundle on one lane with one label that forks toward their other ends. An edge that has to pass the cards of its band leaves by the side of the band nearer to where it goes; edges that run down one side of both bands of a gap go straight through it there, and those with one label are one bundle with one label. Two edges with different labels never run over one another in a gap, and every edge keeps its own path, arrow and label text. The 109-node test fixture went from 2416 × 6252 px to 2416 × 2378 px (its opening zoom in a 1200 × 638 view from 0.102 to 0.268); the collapsed-regions test page got 52 to 78 px shorter in each of its four states
- A scenario's `then` names block events by their full name, as the blocks declare them (`{ event: agentic.work.RunStarted }`, not `run_started`), and a refusal by the block command refused, its error and the rule of the run (`{ refusal: agentic.resource.RequestClaim, error: agentic.resource.NoTimeLimit }`, `{ refusal: agentic.channel.SendMessage, rule: control_without_proof }`), in place of `event: refusal`. `sim scenario check` refuses an event no block declares as `unknown_event`, naming the nearest declared event (so an old name like `run_started` points to `agentic.work.RunStarted`), and a command or error no block declares for it as `unknown_refusal`. - `agenticspec sim` runs a process part like a runtime when it is given runs (a `run` or `order` link, or a trigger): each run executes the steps of its program, `steps` (1 by default), each a turn of the profile role the part names by `role`, and the part reports its runs in its per-part KPIs (`tasks_started`, `run_steps`). `sim check` accepts a trigger link that ends at a process part; `trigger_target_not_agent` refuses one that ends at a part that is not an agent, a runtime or a process

A `shared_read_write` workspace written only by the parts of one single-copy unit was `read_write_many`, which a single-node storage provisioner refuses; it is now `read_write_once`. - The contract of every architecture lists the default ingresses it has, so every contract file and "Contract" section of the docs site gains them, and `agenticspec sim contract` always reads the KPI catalogue
- `agenticspec sim check`, `sim contract`, `packing default` and `deploy bundle` accept the same documents: each runs the check, which refuses a part whose block is no part kind of the architecture block, and every part kind derives its ports (`question`, `process`, `delegation` and a nested `architecture` none of their own); a `harness` part uses `harness.session` and `harness.tool-call`
- A deployment bundle names each pinned runtime by its image reference, `<image>@sha256:<digest>`, in `runtimes` and in a unit's `code`; the binding's runtime needs both `image` (without tag or digest) and `digest`. `deploy bundle` refuses an address in the architecture (a key `address`, `host`, `hostname` or `url`) as `address_in_architecture`: an address is the binding's

- The studio model names who records what `agenticstudio serve` carried out itself: the actor `studio.session.Server` may `studio.draft.ReviseDraft`, `studio.session.AnswerToolCall` and `studio.session.FailToolCall`. A page or an agent still may not send them
- **Breaking:** the component `studio-server` no longer owns `studio.evaluation`, so its surface has no view `studio.evaluation.Evaluations` and no evaluation commands. `agenticstudio serve` never answered them: a simulate is answered in its tool call's answer and records no evaluation. The domain stays declared in the studio model

### Fixed

- Blocks: `agentic.deployment.RollBack` refuses an installation whose replaced installation was rolled back itself (outcome `replaced-not-reactivatable`, error `NothingToRollBackTo`). Before, the rollback ended the current installation and skipped the reactivation, so the runtime held no Active installation
- Blocks: `agentic.store.PutRecord` refuses a put under a key that a record is being written under, not only one a record is present under (`key-taken`, `KeyTaken`). Before, two puts of one key before either was confirmed were both confirmed, so an artifact store held one content twice
- Blocks: `agentic.gateway.AdmitCall` records a call that names an upstream behind another gateway as `NoUpstream` (outcome `no-upstream-foreign`). Before, a gateway with no upstream of its own admitted it
- Blocks: `agentic.architecture.CommitRevision` refuses an architecture with a gateway part that has no link carrying model calls to a model part (outcome `gateway-without-model`, new error `GatewayWithoutModel`), as `agenticspec sim check` already did (`agent_without_model_path`). Before, an agent linked to such a gateway counted as having a path to a model
- Blocks: the summary of `agentic.store.DeleteRecord` no longer says a delete needs an approval by default: no grant is ApprovalRequired by default and the store block does not check a decision
- `agenticspec sim check` accepts `model_share` on a runtime or process part, as on an agent: the simulator already split such a part's model calls by it, and the check refused it (`setting_unknown`). The simulator reads `coordination`, `start_stagger` and `partition` only on agent parts; a runtime or process part's copies take the defaults, as the check's `swarm_needs_agent` and the settings table already said
- The render model (`agenticspec-render-model/1`) draws every edge between two nodes of one region: one between cards that do not stand side by side, or that crosses the frame of a region inside it, runs on a lane of its own below what the region holds. Before, such edges were not drawn at all
